# Design

## Context

See [proposal.md](proposal.md) for motivation and scope. This is planning, not an implemented feature.

Verified current state:

- Next.js App Router/TypeScript, Prisma with PostgreSQL adapter, Supabase authentication/RLS, Stripe SDK and Resend. The package manifest currently specifies Next.js 16.2.9; do not introduce another backend or upgrade Stripe API `2026-05-27.dahlia`.
- `UserProfile.userId` owns tenant data and subscription fields. No organisation/membership model exists; `Customer`/`FinancialContact` represent debtors. The user explicitly selected existing single-owner tenant scope and `platform_owner` only.
- `requireAdminElevation({ minRole: "platform_owner" })` already supports the required auth/role/session layers. The current extension route calls it without a minimum, accepting support/admin too.
- Existing extension reads Stripe, adds days to `trial_end`, updates Stripe, then writes local fields. It has no reason/key/version, no idempotency options or lock, and uses pre-update invoice period data. `logAdminEvent()` catches failures and is not a mandatory audit guarantee.
- Webhook receipt is uniquely persisted but every duplicate is acknowledged even if processing failed. Timestamp comparison and mutation are separate; create/update uses delivered fields despite retrieving a newer expanded subscription. Direct admin writes have no reliable event watermark.
- Dashboard gating is status-only; `getSubscriptionTier()` reads raw tier and `requireFeature()` checks only catalog features. Signup still creates a local 14-day onboarding trial. Existing Stripe-first specs prohibit account-age substitutes for Stripe state but do not define explicit application grants.
- `resolveAllowancePeriod()` uses recorded billing dates, then a creation-to-trial-end window, then Australia/Melbourne calendar month. Reminders use transaction advisory locks. Railway's `claim_due_weekly_debtor_summaries()` and `claim_due_owners_digests()` filter raw `subscriptionTier` in worker SQL; these would omit eligible grants even if execution gates were fixed.
- No dedicated billing contact or subscription charge-dispute model exists. Supabase tenant email is available through `fetchTenantSnapshot()`. `sendOwnersDigest()` and `sendWeeklyDebtorSummary()` demonstrate tenant-directed Resend/template services distinct from debtor follow-up sends.

Task-3.6 inspection on 2026-10-15 confirms partial implementation, not completion: the current schema has the owner journal and `pendingTrialOperationId`, but no customer journal/reservation. `tenantBillingCoordinator` checks direct projection against the owner reservation after provider mutations and supports only an owner fence. Checkout creates customers/sessions and upgrades without durable keys and writes billing through the customer role; portal customer binding is an uncoordinated privileged write. Downgrade creates then updates a schedule; DELETE releases it. Cancel either ends local onboarding access or creates a cancellation portal session, not a direct subscription cancellation. Checkout success still projects through the customer role; the webhook uses the coordinator. The approved extension closes these gaps without marking tasks complete.

### Current specification conflicts addressed

The corrective-action baseline only exposes extension for a `trial-lapsed` diagnostic; replace that constraint. The access-control baseline only understands Stripe status and says canceled revokes subscription access; distinguish eligible application grants rather than falsifying billing status. The allowance baseline promises capacity never interrupts started sequences; clarify that this is not authorization to send after access expires. Reconciliation must preserve independent grant access on subscription deletion, including avoiding destructive base-tier invoice pausing for grant-backed tenants. Other corrective actions and checkout Stripe authority are unchanged.

## Goals / Non-Goals

**Goals:** One server-owned effective entitlement contract; tenant-scoped owner authorization; absolute, recoverable Stripe operations; mandatory audit; precise UTC expiry; bounded grant quotas; independently retryable communication.

**Non-Goals:** Distributed atomicity between Stripe/Resend/Postgres; implementing a new organisation hierarchy; granting access by overwriting billing columns; generic staff permissions or debt adjudication. Billing outcomes remain Stripe-owned; no local “forgive debt” button.

## Decisions

### D1. Tenant identity and authorization reuse

Target path IDs remain `UserProfile.userId`, matching the actual extension route and protected tenant page. Resolve the profile server-side and scope every grant, operation and delivery lookup to it. “Organisation” labels use `displayName` with an explicitly labeled tenant-account fallback. Do not infer the organisation from an accounting connection or debtor record.

All new management endpoints, recovery and retries call `requireAdminElevation({ minRole: "platform_owner" })` before target reads. The existing extension endpoint is an owner-only adapter; diagnostics may link owners to management but cannot retain an alternate mutation path. The existing tenant health view remains available to permitted support/admin staff; owner-only operation details are separate. Guard role/session again for any user-initiated recovery, not just the original mutation. Customer-facing reads derive tenant ID from authenticated identity and use `withUserContext`; admin/system code uses narrowly scoped, commented privileged services.

Approved recovery/session distinction (2026-10-16): preview confirmation remains bound to the original actor and original elevated session. Recovery and its read-only operation-status lookup require the same original actor with a currently active `platform_owner` role and valid fresh elevation, but may use any current elevated session, including a newly elevated session after the original expires. Another owner actor cannot substitute. Keep `TenantTrialOperation.adminSessionId` immutable as the original session; do not rebind the journal or relax preview confirmation, other mutations or notification retry authorization.

Use same-origin checks on cookie-authenticated trial mutation/preview/recovery routes and strict Zod objects; prevent support impersonation from converting a customer session into owner authority. Alternatives rejected: role hiding in UI, treating every elevated staff member as superuser, or new custom superuser flags.

Preserve the full before schema including webhook leases; never use datasource/migration-directory inputs or hand-edit generated/historical migrations. Otherwise use the repository's Prisma workflow only in confirmed isolated scratch/shadow databases. Offline generation is not database validation or application authorization; isolated application/constraint/RLS verification remains pending, and shared application requires separate review:

Reuse `AdminAuditEvent` with `admin_tenant_action` plus structured operation metadata and append-only action subtype `trial_attempt`, `trial_result`, `trial_recovery`, `trial_notification`. Audit before/after snapshots include effective and source-specific expiry, billing/grant plan, required reason, operation ID, result, source, subscription, actor/session, target and UTC timestamp. Keep business reason distinct from error summaries.

For user-initiated recovery, append `trial_recovery` with the current recovering session as the audit event's `adminSessionId` and metadata `originalSessionId` (the immutable operation session) and `recoveringSessionId` (the current session). Preserve original journal attribution and all earlier audit rows, including when both session IDs are equal.

RLS enabled on all new public tables. Grant customer roles only SELECT on their own current grant and safe risk facts, enforced by `auth.uid() = userId`; no INSERT/UPDATE/DELETE for customer or anonymous roles. Journal/delivery/audit rows are server-only with no tenant/anon Data API access. Revoke default privileges explicitly and test grants as well as policies. Check existing `user_profiles` grants: prevent customer updates to `billingAccessVersion`, reservation and existing billing authority columns while preserving legitimate display-name updates through the server. No new SECURITY DEFINER helper. Append-only audit writers expose create only; existing history must not be rewritten by recovery. Audit retention is independent of current-grant replacement.

Alternative rejected: nullable admin expiry columns merged into `trialEndsAt`, because this would confuse billing authority and lose plan/source/history.

Apply RLS/default privilege revocations to `tenant_billing_mutations` and protect `pendingBillingMutationId`: no customer/anon journal SELECT or writes, no customer reservation/version/billing-column writes. Safe customer status reads are scoped server projections, not Data API table access. Privileged journal and verified projection writes are an explicit narrowly justified server-only billing exception, not client billing patches. Existing customer access/ownership reads remain under `withUserContext`. Customers use their journal for durable attempt/result records; do not invent owner/session identities in `AdminAuditEvent`.

Prisma cannot express the customer actor-equals-tenant and owner/customer reservation-exclusivity CHECKs. Keep those in separately reviewed `prisma/tenant-billing-mutation-constraints.sql`, applied after the generated journal migration, never inserted into generated/history SQL. Both remain unapplied in this offline subset. Static contract tests verify declarations/SQL shape only, not live constraints. Reservation tenant/fence validation and write-once evidence still require D6a services; task 3.9 must supply both journal tables' RLS/grants and reservation-column protection before rollout.

#### Approved profile-write clarification (2026-10-14)

Customer roles have no profile INSERT/DELETE or billing-column UPDATE authority. Grant only display-name, onboarding-completion and Prisma lifecycle timestamp UPDATE columns, with existing tenant RLS. Replace the settings profile upsert with an authenticated lookup, the existing idempotent `createUserProfile()` bootstrap only if genuinely missing, and a scoped display-name update. Editing a name must never recreate/reset a present trial. Verify missing-profile bootstrap and existing-profile edits with mocked route tests and live column-privilege checks.

All verified billing writes, including Checkout customer binding, discovered-subscription binding and upgrade projection, use the tenant-scoped privileged billing coordination service rather than the customer Postgres role. Customer authentication/ownership reads remain under `withUserContext`. This documented server-only exception writes verified provider results under the shared lock/version/reservation contract; it is not a generic client-input profile patch. Migrate Checkout creation/upgrade, Checkout success, portal binding, cancel and downgrade writers before deploying column restrictions, preserving purchased-plan behavior. Never grant billing-column privileges back merely to keep a legacy route working.

### D3. Effective entitlement resolver and precedence

Extend `lib/billing.ts` around a pure resolver plus user-context and privileged/batched loaders. Resolve a fresh snapshot at an explicit server `now`: billing profile, grant and blocking risk facts. Return `allowAccess`, `effectiveTier` (nullable when denied), `source`, `effectiveAccessExpiresAt`, separate `effectiveTrialExpiresAt`, `effectiveExpirySource`, `stripeTrialEndsAt`, grant details, warnings/restriction and state version. Sources are `paid`, `stripe_trial`, `admin_grant`, `onboarding_trial`, `past_due_grace`, `none`.

For healthy trial-only access with multiple independent sources, effective trial/access expiry is the latest valid source expiry, while current plan/source follows the precedence below. Return expiry provenance separately: a Stripe trial can supply the current plan while a retained longer admin grant supplies later continuity. Show that later continuity with its own plan, not as a promised Stripe-plan extension. Duration extensions use that full effective expiry, not merely the date of the currently preferred source. Paid/grace access has no trial-derived access cutoff; do not reinterpret a billing period end as trial expiry. If Stripe remains trialing past its recorded end, preserve its authoritative status behavior, label timing pending reconciliation, and use at least server now as the extension base.

Precedence and eligibility:

1. A real active Stripe subscription retains its paid plan regardless of retained grant. Billing disputes do not use grants to enhance or replace any existing paid policy.
2. `past_due` retains existing warning/grace and billing plan; grants are suppressed. `unpaid`, `incomplete`, `incomplete_expired`, unresolved invoice debt or unresolved/lost subscription disputes cannot obtain grant access. Unknown subscription/risk states fail closed for grants. Billing resolution routes remain reachable.
3. Suitable current Stripe `trialing` remains Stripe-plan access. Its persisted Stripe trial date is display/extension data, not a local account-age substitute for authoritative status. Do not implement a general Stripe-trial termination timer in this feature.
4. A nonrevoked grant supplies its catalog plan iff `startsAt <= now < expiresAt` and billing risk allows it. Retained grants may coexist with a later independently created Stripe trial/subscription but never change its tier. Paid/Stripe sources take precedence; a remaining eligible grant can provide continuity after that source ends. No new grant while a suitable live Stripe trial exists.
5. Without any Stripe subscription, an existing signup `trialing` record with a future recorded expiry remains bounded `onboarding_trial` access. An eligible grant takes precedence over onboarding plan, with grant expiry required to extend the current effective trial expiry. On grant revocation the still-valid onboarding source remains. Local `active` without a subscription, missing profiles and unknown statuses do not imply perpetual paid access.
6. Otherwise deny gated access. Accounting/catalog defaults do not grant access. Check expiry before every request authorization and immediately before job side effects; never cache access across requests or jobs past its expiry. A request already authorized is not canceled mid-flight; queued jobs must reauthorize on execution.

Trial management eligibility is stricter than access: block grant/extend for paid or any billing restriction, even where grace access remains. Debt-free `canceled`, `paused`, no-subscription and expired onboarding tenants can receive application grants; `paused` must not be resumed. If a Stripe trial exists but has a schedule, cancellation flags, pending update, unsupported/multiple billing items or cannot be safely extended, block with billing guidance rather than automatically choose application-only mode. Revocation remains allowed for a current grant under any billing status.

Preserve catalog `hasPlanFeature()` and implementation readiness flags; `requireFeature()` first checks access then the effective plan. Keep pure tier-limit helpers, but change their callers to pass the resolver's tier. Public grant input uses a strict four-plan enum rather than forgiving `normalizeSubscriptionTier()` aliases. No pricing or tier-feature changes.

#### D3a. Approved narrow platform-owner internal access (2026-10-18)

This amendment qualifies D3's unlinked-active denial only for the platform owner's own internal account. After all real Stripe/grant/onboarding sources, allow `source: platform_owner` iff an existing profile has status exactly `active`, a recognized existing catalog tier (including existing legacy aliases), no linked Stripe subscription, a fresh server-owned fact proving its own role exactly `platform_owner` and status exactly `active`, and no blocking or unknown billing risk. Missing facts default false; role lookup errors fail closed. Canceled/cancelled, paused, delinquent, incomplete, trialing, unknown or missing profiles cannot use this fallback. Keep effective access/trial expiry and expiry provenance null; this is neither paid nor trial access and is not a trial operation source.

Use an uncached server-only privileged read of `platform_roles` only: exact-user unique lookup selecting role/status; batched lookup selects userId/role/status for requested IDs in one query, never N+1. Document this narrow RLS bypass; do not grant tenant SELECT or bypass tenant-data RLS. Pass only a boolean internal fact to the resolver, never role rows or this fact in returned profile/client shapes. Auth and admin elevation remain unchanged, with no client flag, JWT assertion or email allowlist. Every loader (tenant snapshot, dashboard, allowance, system single/batch) and direct resolver projection (admin target, preview, grant/revoke, recovery and notification) must use the target profile owner's fact, never the operator's. Preserve current Stripe eligibility/preflight, purchased-plan controls, prices, proration and operation-source enums.

Apply the same decision to dashboard/API/features/chase/jobs, retaining existing catalog limits and accounting windows, monthly AI usage and pre-send freshness. Label the source “Platform owner internal access” in exhaustive safe presentation/audit/notification contracts, without subscription/trial or charge claims. Verify eligibility/denial/precedence, exact role scopes/selections, freshness/revocation, constant-query batches, dashboard/chase parity, reminder/AI inheritance and safe schema projections using mocks only. No schema/env/install or database/provider access is part of this follow-up; document working-tree status and keep external gates open.

### D4. Time, preview and API contracts

Use elapsed days (24 hours), not calendar-day arithmetic across DST. The browser shows an IANA timezone and explicit UTC offset. Specific times submit ISO-8601 with offset, normalized to integer UTC seconds; missing offset, DST gaps/ambiguity, non-future or unsafe horizon are rejected. Proposed minor guardrail: application grants cannot end more than 730 elapsed days from confirmation; Stripe additionally enforces its documented anchor-based horizon. Extension expiry must be later than all currently valid effective trial expiry. Revocation is the only shortening action and affects only grants.

New routes under `/api/admin/tenants/[id]/trial-access`:

| Method/path | Contract |
| --- | --- |
| `GET` | Owner-only safe management snapshot, resolved billing contact/provenance, current sources, version, allowed actions/restrictions. Read-only Stripe refresh where linked; return unavailable rather than pretend eligibility if Stripe fails. |
| `POST /preview` | Strict `{ operationId, action: extend_or_grant | revoke_grant, days?: 7 | 14 | 30, expiresAt?: offset-ISO, plan?: publicTier, reason, notify: false by default, timeZone, expectedVersion }`. Exactly one days/expiry for extension/grant; plan mandatory for application grant and forbidden for Stripe-only extension. Persist owner/tenant-scoped 15-minute preview with immutable normalized input and frozen absolute target. Return predicted source, plan, UTC expiry, local display, billing effect and preview version. No access mutation or email. |
| `POST /operations` | `{ operationId, expectedVersion }`; load the original actor/session's preview and immutable input, verify TTL, source/eligibility and unchanged billing fingerprint/version, then confirm. Never recalculate and silently move the previewed expiry. Invalid/stale input requires a new preview/operation ID. |
| `GET /operations/[operationId]` | Tenant/original-actor-scoped stored operation state/result and separate notification outcome; require current active owner role/elevation, not the original session ID. Read-only recovery lookup permits the same actor's newly elevated session; no mutation or other-owner substitution. |
| `POST /operations/[operationId]/reconcile` | Same-original-actor recovery with current active owner role/elevation in any session; reuse the frozen expiry/key, preserve original journal session and append current-session recovery audit per D2. Never grant extra days. |
| `POST /operations/[operationId]/notification/retry` | Owner-only delivery-only retry for requested notifications, subject to provider outcome safety and tenant matching. |

Return 400 validation, 401/403 existing guard distinctions, 404 scoped absence, 409 stale/ineligible/in-progress/key conflict, 502 definitive upstream rejection, 503 unavailable eligibility/persistence. Completed access change returns 200 with notification status, even if email failed. Uncertain Stripe state returns 202 with operation ID and reconciliation guidance; UI polls read status only on a bounded cadence, without mutation retry loops. Replays of a completed identical operation return the original outcome. A read-only status lookup can show later notification status separately from the immutable access result.

Keep `/actions/extend-trial` as an adapter accepting the new safety envelope and Stripe-extension-only intent, including preview-backed operation ID/version. Reject old `{days}` bodies. Replace the diagnostics component's old generic day action; it opens management instead. No weak legacy route remains.

### D5. Stripe restrictions and billing-risk evidence

Official documentation checked during planning on 2026-10-14:

- [Pinned subscription update API](https://docs.stripe.com/api/subscriptions/update?api-version=2026-05-27.dahlia): `trial_end` is Unix seconds; changes the billing anchor; at most two years from `billing_cycle_anchor`; incompatible with `trial_from_plan=true`.
- [Legacy free trials](https://docs.stripe.com/billing/subscriptions/trials/free-trials): 730-day maximum trial guidance, existing trial updates supported, paused trials need resumption to restart. This feature never resumes them.
- [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests): POST options support keys; cached results include failures; keys may be removed after at least 24 hours; parameters must match.
- The general trials documentation now recommends [Trial Offers](https://docs.stripe.com/billing/subscriptions/trials), requiring API `2026-09-30.endive` or later and not supporting trial-length changes. Do not adopt it or upgrade the pinned API.

Use existing `retrieveSubscriptionWithLatestInvoice()` and factor one shared Stripe snapshot mapping/reconciliation helper. Only update `trial_end` with `proration_behavior: "none"` and stable operation-derived `idempotencyKey`. Do not pass items/prices, anchor reset, cancellation, schedules or collection behavior. Display that extending a Stripe trial changes its first-billing timing; do not promise no future charge or change unrelated cancellation intent. Recheck exact rules against pinned docs/SDK before implementation's mocked parameter and boundary tests; optional Stripe test-clock verification is manual/test-mode only, never part of unit tests.

Read fresh linked customer/subscriptions, relevant subscription invoices and subscription charges/disputes before grant/extension. Validate all customer/subscription/metadata identifiers consistently; a deleted customer, ambiguous multiple subscriptions, unmapped price or unreadable risk is blocked, not a debt-free assumption. No Stripe customer means no Stripe billing history to inspect. Ignore Connect/debtor charges entirely. Map disputes via billing charge/invoice to the tenant's subscription, not metadata alone; paginate the applicable Stripe records to avoid missing old outstanding debt. Unknown mappings for potentially relevant subscription charges block eligibility until resolved.

Persist blocking invoice facts for failed/overdue outstanding subscription invoices and `uncollectible` debt. Clear only after Stripe confirms that specific invoice is paid or void, not after unrelated `invoice.paid` or cancellation. Treat dispute states `warning_needs_response`, `warning_under_review`, `needs_response`, `under_review`, `lost` as blocking; verified `won`, `warning_closed`, `prevented` can clear that dispute fact. Lost disputes cannot be forgiven with grants; use existing billing/support resolution outside this feature. Track `charge.dispute.created/updated/closed`, relevant invoice status changes, and retrieve authoritative current objects when needed. Document required additional subscribed webhook events in the Stripe runbook. Existing billing portal/support is the resolution destination, not a fabricated in-app debt workflow.

Alternative rejected: status-only eligibility, which would let cancellation or a disputed paid charge bypass obligations. Grants rely on persisted signed-event risk facts after creation; delayed external events are an unavoidable visibility lag, not justification to ignore known risk.

### D6. Mandatory audit, locking, idempotency and recovery

Add a transaction-aware mandatory mode/helper in `lib/admin/audit.ts` reusing the existing event mapping. It takes a transaction client and propagates errors; keep unrelated callers' current semantics unchanged. Trial grants/revocation cannot use only error-suppressing logging. Before any external mutation, commit the pending operation/reservation and `trial_attempt` audit. Local grants/revokes and `trial_result` audit commit in one transaction with the version increment and notification outbox entry.

Use the existing advisory transaction-lock convention with a distinct `billing-access:<userId>` key, parameterized SQL, and consistent lock ordering. All billing writers touching these fields (webhook, Checkout creation/upgrade/success, portal binding, cancel and downgrade) use the same coordinating service. UI optimistic version checks remain necessary even with serialization: two previews must not become two cumulative extensions. Unique operation IDs and stored hashes enforce long-lived replay safety independent of Stripe's cache.

Stripe mutation saga:

1. Validate preview ownership/hash/version and fresh Stripe/risk fingerprint; under the tenant lock claim durable reservation, record attempt and persist the frozen absolute expiry and provider key. If another unresolved operation exists, conflict.
2. Make Stripe call outside the DB transaction. Execution lease/fencing protects duplicate executors; no other admin mutation may claim the tenant while outcome is unknown. A lease expiring does not delete the reservation or start a different operation.
3. On a definitive Stripe validation/API rejection, atomically record failure/audit and release reservation. On timeout, cached 500, connection loss or uncertain outcome, leave reconciliation required. Do not create a fallback grant.
4. On success, fetch current authoritative subscription/risk state and coordinate a fenced commit with billing reconciliation. Persist only confirmed current Stripe values, not previous invoice dates or a local maximum. Finalize success/audit/outbox and release reservation atomically. If a genuinely newer billing state superseded the result, preserve that state and report a superseded operation result, not stale access.
5. If final DB commit fails, the original attempt/key remain durable. Webhook reconciliation or explicit owner recovery retrieves current Stripe state and appends the missing result once. Within Stripe's retained-key window, identical absolute request retry is allowed; beyond it, do not blindly repost. Retrieve current state and reconcile evidence of the original result; if not provable, keep unknown for owner review rather than applying another mutation.

Webhook ledger processing uses statuses and fenced claims (`received/processing/processed/skipped/failed`) with transactionally durable result. A unique received row is not completed work. Failed/interrupted processing is retryable; concurrent processing does not acknowledge a merely in-flight event as terminal success. Serialize reconciliation and validate snapshot/version before commit; re-fetch on conflicts. Event timestamps are useful stale hints but not sufficient for ties or direct writes. Current Stripe reads and per-tenant fencing prevent mixing old status/price with newer period data. Do not set event watermarks to local server time. Ignore obsolete subscription events after verifying the current customer/subscription binding; initial binding still uses authenticated checkout metadata and tenant mapping.

Mutating billing endpoints conflict with either unresolved reservation. Owner confirmation, including local grant/revoke, conflicts with unresolved customer operations; no owner Stripe reservation can start while a customer outcome is unknown. Webhooks can reconcile true current billing state without waiting indefinitely, but cannot clear either reservation merely because state changed, an event arrived or a lease expired. Finalization requires operation-specific provider evidence and the current fence. No audit rows are updated to turn a failure into success: append recovery result and reference the operation. Durable accepted attempts provide evidence even when no result could yet be committed.

#### D6a. Approved durable customer billing mutations (2026-10-15)

Use a separate customer journal rather than weakening the owner/preview/audit contract. Extend the coordinator with discriminated owner/customer fences and a shared reservation check. Lock order remains tenant, then operation/event fence. Acquire, hand off and release reservations, verified customer/discovered-subscription binding, local cancellation and all billing/risk/grant writes under `billing-access:<userId>`. Increment `billingAccessVersion` on reservation acquisition/release as well as access changes. Owner preview fingerprints include both reservation identities; intervening customer activity invalidates a preview even if eventual subscription state is unchanged. No locks or DB transactions span a provider mutation call.

When no customer exists, atomically persist the root intended action and a child `customer_create` journal linked to its caller UUID with a server-derived stable step identity, and reserve the child under the tenant lock. Root execution waits for the child. After verified customer binding, atomically finalize the child and hand off the reservation to the root. Store the post-binding execution version on the root. A crash leaves either the child or root reserved and recoverable; root retry recovers its prerequisite, never creates another customer. No independently executable unreserved root may dispatch. Each provider step stores a write-once normalized request/hash, method/object target, distinct operation/step-derived key, provider IDs/request ID and sanitized evidence, attempts, first-attempt time and outcome. Freeze all config-derived values, prices, URLs and metadata; retries cannot regenerate them from changed env vars. The immutable business-intent hash excludes dynamic provider results; later-step derived params are frozen before that step's first call. Commit journal/reservation before external mutation; commit first-attempt time before dispatch, conservatively anchoring that step's 24-hour retained-key replay deadline. Requests/keys survive process death; never log or return email/raw payloads/secrets.

Claim a short execution lease with a monotonically increasing fencing token under the lock. Recovery can reclaim an expired lease, but cannot release the reservation. Before dispatch and every step/result commit verify tenant, reservation, current binding, lease and fence. Recovered/stale executors can at most replay the identical keyed step within the original window; a stale executor cannot advance steps, commit state or clear another reservation. Terminal commit atomically stores safe response/current verified provider projection, status, reservation release and version increment. `superseded` requires proof the step outcome is known and genuinely newer state made its projection obsolete; it never means unknown or lease expiry.

Timeout, connection loss, cached provider 500, success followed by DB failure and interrupted dispatch remain `reconciliation_required` (or durable `pending` awaiting lease recovery). Use `failed` only for definitive nonexecution/rejection once every attempted step is known. Schedule-create success plus phase-update rejection remains reserved/reconciliation-required until intended phases are verified or separately reviewed resolution proves safe closure. Never auto-release/delete a schedule, compensate billing, choose a new key, or repeat creates to escape uncertainty.

Recovery performs one explicit bounded attempt, not a loop. Retrieve known customer/session/subscription/schedule IDs; validate tenant/customer/subscription binding, operation correlation and intended current state. Within `firstAttemptAt + 24 hours` for that step, recover an unknowable result by identical request/key replay; cached failures stay uncertain absent proof of no effect. Create recovery needs a unique attributable object or verified provider-request evidence. Unknown customer/Checkout/schedule/portal creation stays reserved for operator/provider investigation, never blind recreation. Do not assume portal-session retrieval exists in the pinned SDK; use stored result or retained-key replay, otherwise block unknowable late creation. Existing bounded billing access is not revoked merely for uncertainty.

## Risks / Trade-offs

- [External services are not atomic with Postgres] → Durable attempt/reservation, absolute targets, provider keys, fenced commits and explicit uncertain outcomes.
- [Direct Stripe Dashboard edits can race reads] → Fresh preflight and result reconciliation, conflict on fingerprint change; do not promise distributed locking over external manual edits.
- [Many raw-tier consumers and worker SQL filters] → Explicit conversion inventory, feature-gate and execution tests; broader worker candidate sets avoid duplicated logic.
- [Spec/code disagree on onboarding authority] → Preserve the actual bounded pre-checkout trial as its own source; never relabel it Stripe-managed or migrate dates into grants.
- [Webhook delivery lag] → Fresh owner-operation preflight, persisted independent risk facts, signed retries; documented unavoidable lag before an externally changed billing fact becomes observable.
- [Provider key expiry] → Local long-lived journal and blocked unknown-outcome retries after the provider window.
- [RLS SELECT may expose private operator metadata] → Tenant-readable grant contains safe access facts only; all reason/audit/journal/delivery details remain privileged.
- [Broad rollout needed for automatic expiry] → Deploy shared resolver and jobs before enabling owner UI; retain granted records and audit on rollback, never silently drop live access.
