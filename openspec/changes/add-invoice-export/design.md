## Context

See proposal.md - Why. This design adds an export path that is the inverse of `openspec/changes/add-csv-xlsx-invoice-import`, reusing its conventions: the already-installed `xlsx` package (SheetJS Community Edition `^0.18.5`), tenant scoping via `withUserContext`, and the existing `csv_export` plan-feature flag in `lib/subscriptionPlans.ts` (currently in `UNIMPLEMENTED_FEATURES`, gated `true` for `small_business` and `accountant_partner`, `false` for `starter`/`solo`).

Two facts materially shape the design:

1. **The dashboard invoice list has no pagination and only one existing filter dimension today.** `app/dashboard/invoices/page.tsx` loads the full active-or-resolved status bucket in one query (`loadDashboardInvoices`) and applies a single categorical overview-card filter (`?filter=overdue|broken_promises|held|disputed|bounced|overdue_60_plus|no_contact_email|import_anomalies` via `filterInvoicesByOverviewCard`). There is no existing customer, date-range, search-term, or accounting-source filter UI on that screen. The "current invoice view" the dashboard Export button exports is therefore: the active status bucket (active vs. resolved) plus whichever overview-card filter is applied — not a richer ad-hoc filter set, because that richer filter set does not exist on this screen.
2. **`TrackedInvoice` has no canonical "invoice date" field.** Only `dueDate` (always present) and `createdAt`/`updatedAt` (always present) are guaranteed on every row regardless of source. An `invoice_date` value only exists inside the JSON `providerMetadata` column, and only for `provider = "spreadsheet_import"` rows that had it mapped at import time (`lib/invoiceImport/mapping.ts`). Stripe/Xero/MYOB-sourced rows do not carry a canonical invoice-date value.

## Goals / Non-Goals

**Goals:**
- Export `TrackedInvoice` data (plus related customer, payment, promise-to-pay, and dispute state) as CSV or XLSX, tenant-scoped and gated by the existing `csv_export` feature.
- Provide a quick export of the current dashboard view and an advanced, richer-filtered export from a new Settings screen, backed by one shared filter/query service so filtering logic is not duplicated.
- Protect against spreadsheet formula injection in both formats without corrupting legitimate numeric/date values.
- Keep implementation synchronous and dependency-light, matching this product's realistic invoice volumes, while documenting a clear path to background processing if volumes grow.

**Non-Goals:**
- Building generic ad-hoc filtering (arbitrary saved views, complex boolean queries) — only the specific filters named in the proposal (status, customer, accounting source, date range on a specific field) are in scope.
- Adding pagination to the dashboard invoice list — out of scope; the dashboard Export button exports what that screen already shows (status bucket + overview-card filter).
- Introducing a new persisted, user-facing audit-log model. PaidSoon has no such model today (`docs/DDD.md` §15: "Audit model: none. `email_logs` is the only persistent event record" — the only persisted audit trail in the codebase, `lib/admin/audit.ts`, is scoped to internal admin/staff actions, not tenant users). Export events are recorded via the existing `lib/diagnostics/server.ts` `traceEvent` structured-logging convention already used on `app/dashboard/invoices/page.tsx`, consistent with how the rest of the dashboard observes user actions — not as a new persisted table.
- Background/async job infrastructure (queues, worker processes) for export generation.
- Any new Prisma model, migration, or environment variable.

## Decisions

- **Reuse `xlsx` (SheetJS CE), not a new library.** It is already a dependency (via invoice-import) and already used for AOA/JSON-to-sheet generation, `!cols` column widths, and `!autofilter` worksheet properties, both of which are supported in the installed Community Edition's writer. Cell-level style objects (bold fonts, fill colors) are a SheetJS Pro capability not available in the installed community package, and — verified directly against the installed `xlsx@0.18.5` writer source — **frozen panes are not serialised by this package's XLSX writer either** (`write_ws_xml_sheetviews` only ever emits `rightToLeft`/`workbookViewId`, never pane-freeze state, regardless of what a caller sets on the worksheet object). The "styled, navigable header row" requirement is therefore satisfied using the CE-supported affordances that actually work at write time — autofilter and column widths — with a distinct header row for visual emphasis; true font/fill styling and frozen panes are both treated as a nice-to-have follow-up requiring a future library change (e.g. SheetJS Pro or a different writer), not a blocking requirement, and this trade-off is called out explicitly rather than silently downgraded.
- **CSV encoding: UTF-8 with a BOM.** A UTF-8 byte-order-mark is prepended to the CSV output specifically because Microsoft Excel (the most common consumer, per the compatibility requirement) misinterprets BOM-less UTF-8 CSVs containing non-ASCII characters as a legacy code page. Google Sheets, Apple Numbers, and LibreOffice all handle a leading BOM correctly, so this is a net compatibility win with no downside for the other three target applications.
- **CSV quoting**: RFC 4180-compliant — any field containing a comma, double quote, or line break is wrapped in double quotes with embedded quotes doubled (`"` → `""`); line breaks within a field are preserved (not collapsed), unlike the import template's simpler `csvEscape` helper in `lib/invoiceImport/template.ts` which collapses newlines — the export helper is a distinct, stricter implementation because reversibility (multi-line notes must read back correctly) matters more for exported data than for a short sample template row.
- **Formula-injection sanitisation**: applied only to user-controlled text fields (customer name/email, promise/dispute free-text notes) — never to system-computed numeric, date, boolean, or enum-status fields (amounts, dates, currency codes, statuses), so a legitimately negative adjustment or a due date is never touched. A cell value is considered "at risk" if, after trimming, its first character is `=`, `+`, `-`, or `@`. At-risk values are neutralised by prefixing a single leading apostrophe (`'`) — the standard "force text" spreadsheet convention — which both Excel/Numbers/Sheets/LibreOffice render as literal text and which, applied in both the CSV and XLSX writers, satisfies "do not interpret as a formula" without altering the underlying characters the user typed (round-trip: strip a leading `'` to get the original value back). This mirrors (and can share a helper with) the sanitisation posture already required of `lib/invoiceImport/**` for parsed/echoed values.
- **Shared filter/query service**: a new module (not part of this design doc's naming commitment, finalized during implementation, e.g. `lib/invoices/exportQuery.ts`) exposes one function that both the dashboard quick-export and the Settings advanced-export route call, taking `{ userId, statusBucket?, overviewFilter?, statuses?, customerId?, provider?, dateField?, dateFrom?, dateTo? }` and returning the same `withUserContext`-scoped, tenant-safe invoice set (with the same joined customer/payment/promise/dispute rows) used to build export rows. The dashboard quick-export calls it with the status bucket + overview-card filter already active on the page (reusing `filterInvoicesByOverviewCard` for the categorical part rather than re-implementing it); the Settings screen calls it with the richer filter set. Neither path re-implements invoice-matching logic independently.
- **Date field selection is scoped to two reliable fields, plus one best-effort field.** Because only `dueDate` and `createdAt` are guaranteed non-null on every `TrackedInvoice` regardless of source, the Settings advanced-export date-range filter only filters by "Due date" or "Created date". "Invoice date" is still offered as an **exported column** (sourced from `providerMetadata.invoice_date` when present, i.e. only for spreadsheet-import-sourced invoices — empty otherwise) but is not offered as a date-range **filter** field, because filtering by a field that is null for most rows would silently and confusingly exclude non-import invoices. The Settings screen's caption ("this range is matched against due date / created date") reflects this.
- **Derived export columns** (documented once here, referenced rather than re-derived elsewhere):
  - `outstanding_balance_cents`/`outstanding_balance`: `computeOutstanding(invoice, payments)` from `lib/invoices/payments.ts` — the exact function already used for the invoice's outstanding balance elsewhere in the product.
  - `paid_date`: the invoice's `updatedAt` timestamp **only when** `status === "paid"`; empty otherwise. There is no dedicated `paidAt` column, so `updatedAt` at the point the ledger fully covers `amountDue` (per `recordInvoicePayment` in `lib/invoices/payments.ts`) is the closest available signal and is documented as such rather than presented as an exact payment-received timestamp.
  - `promise_to_pay_status` / `promise_to_pay_date`: from the invoice's most-recently-created `PromiseToPay` row (`orderBy createdAt desc`, first row) — same ordering already used by `loadDashboardInvoicesWithTx` and the frontend's `getP2PStatus`. Empty when the invoice has no promises.
  - `dispute_status`: `"disputed"` when `status === "disputed"`; `"resolved"` when `disputeResolvedAt` is set; otherwise `"none"`.
  - `reminder_status`: derived from `currentStage` (0–3) and `status`, rendered as e.g. "Not yet chased" / "Reminder 1 of 3 sent" / … / "Sequence complete", matching the existing `STAGE_LABELS`/`STATUS_LABELS` maps in `components/dashboard/InvoiceTable.tsx` (reused, not re-implemented).
  - `accounting_source`: `provider` mapped to a display label ("Stripe", "Xero", "MYOB", "Spreadsheet import"), reusing the same label mapping pattern already used in `lib/admin/diagnostics/checks/sync-stale.ts`.
- **Synchronous generation with a row-count ceiling.** Given tier caps (10/50/200/unlimited chased invoices per month) and that exports read already-created historical rows (not bounded by the monthly chase allowance), a single export could in principle span many thousands of rows for a very long-lived Accountant Partner tenant. Rather than build background-job infrastructure now, the export endpoint streams the response (avoiding buffering the whole file in memory) and enforces a documented maximum row ceiling (e.g. 50,000 rows) beyond which the request fails with an actionable "narrow your filters or contact support" error rather than exhausting server memory or timing out silently. If usage data later shows this ceiling is regularly hit, background/async generation (e.g. a job record + polling/download-when-ready flow, similar in shape to `InvoiceImportBatch`) is the documented follow-up, not built now.
- **Duplicate-request prevention is client-side + idempotency-friendly, not server-locked.** The Export button disables itself and shows a generating state for the duration of the in-flight request (standard React state, matching the existing `bulkActionLoading` pattern in `InvoiceTable.tsx`). The server does not need a distributed lock because export generation has no side effects on invoice/customer data — at most, redundant concurrent requests do redundant read-only work, which is acceptable at this product's scale.
- **No new audit-log table.** Per the Non-Goals above, export requests are recorded through the existing `traceEvent` diagnostics convention (operation `"export_invoices"`, with outcome, row count, and filter shape — never raw customer PII — in the trace payload), consistent with how every other dashboard action in this codebase is currently observed.

## Data Dictionary

All timestamps are rendered in ISO 8601 (`YYYY-MM-DDTHH:mm:ssZ`) in CSV and as native XLSX date cells (format `yyyy-mm-dd`) in the workbook. All amount fields are rendered as a plain decimal with 2 dp (e.g. `1650.00`) in CSV and as native XLSX numeric cells formatted `#,##0.00` in the workbook — both derived from the stored integer-cents value divided by 100. Booleans are not part of this dictionary (no boolean fields are exported). Empty values are rendered as an empty CSV field / empty XLSX cell, never the literal text "null" or "undefined".

| Column | Source | Description | Type | Empty? | Formatting | CSV | XLSX |
|---|---|---|---|---|---|---|---|
| `invoice_reference` | `TrackedInvoice.externalId` | Invoice number/reference from the connected source | string | No | as-is text | ✓ | ✓ |
| `customer_name` | `TrackedInvoice.clientName` | Debtor/customer display name | string | No | as-is text, formula-sanitised | ✓ | ✓ |
| `customer_email` | `TrackedInvoice.clientEmail` | Debtor/customer email | string | No | as-is text, formula-sanitised | ✓ | ✓ |
| `invoice_date` | `TrackedInvoice.providerMetadata.invoice_date` | Invoice issue date — only populated for spreadsheet-import-sourced invoices; empty for Stripe/Xero/MYOB-sourced rows, which have no canonical invoice-date field | date | Yes (provider-dependent) | ISO date / XLSX date cell | ✓ | ✓ |
| `due_date` | `TrackedInvoice.dueDate` | Invoice due date | date | No | ISO date / XLSX date cell | ✓ | ✓ |
| `original_amount` | `TrackedInvoice.amountDue` ÷ 100 | Original invoice total (fixed at creation; not reduced by payments) | decimal | No | 2 dp decimal / XLSX numeric `#,##0.00` | ✓ | ✓ |
| `outstanding_balance` | derived: `computeOutstanding(invoice, payments)` ÷ 100 | Current amount still owed | decimal | No | 2 dp decimal / XLSX numeric `#,##0.00` | ✓ | ✓ |
| `currency` | `TrackedInvoice.currency` | ISO 4217 currency code, upper-cased | string | No | 3-letter code | ✓ | ✓ |
| `status` | `TrackedInvoice.status` | Raw lifecycle status (`pending`\|`paid`\|`paused`\|`snoozed`\|`sequence_complete`\|`manually_resolved`\|`disputed`) | string | No | as-is | ✓ | ✓ |
| `paid_date` | derived: `TrackedInvoice.updatedAt` when `status = "paid"` | Best-available signal for when the invoice was fully paid (see Decisions) | date | Yes (only when paid) | ISO date / XLSX date cell | ✓ | ✓ |
| `promise_to_pay_status` | derived from most-recent `PromiseToPay.status` | `active`\|`kept`\|`broken`\|`superseded`, or empty if no promise exists | string | Yes | as-is | ✓ | ✓ |
| `promise_to_pay_date` | derived from most-recent `PromiseToPay.promisedPayBy` | Date promised, if any | date | Yes | ISO date / XLSX date cell | ✓ | ✓ |
| `dispute_status` | derived from `status`/`disputeRaisedAt`/`disputeResolvedAt` | `disputed`\|`resolved`\|`none` | string | No | as-is | ✓ | ✓ |
| `reminder_status` | derived from `currentStage`/`status` | Human-readable chase-sequence progress (see Decisions) | string | No | as-is | ✓ | ✓ |
| `accounting_source` | `TrackedInvoice.provider` | `Stripe`\|`Xero`\|`MYOB`\|`Spreadsheet import` display label | string | No | as-is | ✓ | ✓ |
| `created_at` | `TrackedInvoice.createdAt` | When PaidSoon first tracked this invoice | timestamp | No | ISO 8601 / XLSX date cell | ✓ | ✓ |
| `updated_at` | `TrackedInvoice.updatedAt` | Last time this invoice record changed | timestamp | No | ISO 8601 / XLSX date cell | ✓ | ✓ |

Explicitly excluded (per proposal's "avoid internal implementation details/secrets" rule): the invoice's own internal `id` (cuid, not requested), `invoiceConnectionId`, `stripeConnectAccountId`/any credential or access-token field, and the full `providerMetadata` blob (only its `invoice_date` key, if present, is surfaced — the rest is provider-internal).

## Risks / Trade-offs

- [SheetJS Community Edition cannot apply cell fill/font styling, and its writer does not serialise frozen panes] → Use the CE affordances that do work at write time (autofilter, column widths, a visually distinct header row) instead of true bold/colored styling or a frozen header row; document this as a known cosmetic limitation rather than silently claiming support the installed writer cannot produce.
- [`invoice_date` is null for the majority of non-import-sourced invoices] → Documented explicitly in the data dictionary and excluded from the date-range filter's selectable fields; only `due_date`/`created_date` are filterable date fields.
- [Very large tenants could produce very large exports] → Streamed generation plus a documented row-count ceiling with an actionable error; background job processing is a documented, deferred follow-up rather than built now.
- [Formula-injection sanitisation could be over-applied to legitimate values] → Sanitisation only touches user-controlled text fields, never numeric/date/status fields, and is verified by dedicated tests asserting negative amounts and past dates are unaffected.
- [No distributed request lock] → Acceptable because export generation is read-only; redundant concurrent requests cost extra read work, not data corruption.

## Migration Plan

1. Add the shared export filter/query module reusing existing invoice-loading and overview-card-filtering code; add the export-generation module (CSV + XLSX writers, shared data-dictionary mapping, and the formula-injection sanitiser) alongside `lib/invoiceImport/**`.
2. Add the export API route(s) with `requireFeature(userId, "csv_export")` and `withUserContext` tenant scoping, streamed response, and the row-count ceiling.
3. Add the dashboard Export button next to "Import invoices" on `/dashboard/invoices`, wired to the shared query module with the page's already-active filters.
4. Add the Settings "Invoice exports" tab and advanced export form, wired to the same shared query module with its richer filter set.
5. Remove `csv_export` from `UNIMPLEMENTED_FEATURES` in `lib/subscriptionPlans.ts`; update the pricing page label via `lib/planPresentation.ts`.
6. Update `docs/DDD.md` (§3, §7, §11, §15) and any other documentation identified in tasks.md.
7. Ship behind normal review/testing; no feature flag is required beyond the existing `csv_export` plan gate, since the plan gate itself controls exposure by tier.

## Open Questions

None. The two material ambiguities in the original request (the "current view" filters that don't yet exist on the dashboard screen, and the non-canonical "invoice date" field) are resolved above as design decisions rather than left open, because both would change the spec-level behavior if left unresolved.
