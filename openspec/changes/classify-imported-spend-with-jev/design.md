# Design

## Context

See proposal.md for motivation and scope. Spend ingestion currently writes `ImportedBill` and `ImportedBankTransaction` rows using provider/source IDs, and those tables preserve provider fields and raw source data. Provider account semantics are not uniform: MYOB bill `Category` is expense coding, while the current Xero bank-transaction adapter maps the bank account into generic account fields. Xero `SPEND` amounts are also positive while MYOB spend transactions are negative. Classification must not mistake a cash account for an expense account or infer flow direction from inconsistent signs.

Existing MarginGuard rules and assignments describe cost semantics (`DIRECT_COST`, `OVERHEAD`, etc.), so they are a pattern for precedence and auditing but not storage to reuse. User-facing changes must use authenticated tenant context and RLS; service-role processing must scope each source record, category, and rule to the same persisted tenant. TypeSafe Jev has a typed Choice API and returns a selected option, probabilities, confidence, model version, and token usage, but no explanation text.

## Goals / Non-Goals

**Goals:**
- Add a stable, tenant-owned analytical category and optional tag layer for existing imported bills and bank transactions, retaining provider facts unchanged.
- Resolve deterministic classifications before asking Jev, preserve user corrections, and expose suggestions for review rather than silently treating AI as authoritative.
- Make category totals safe for SpendLeak, Cost Guard, and MarginGuard consumption, with unresolved values visible rather than folded into confirmed totals.
- Isolate AI failures from provider import success and make work retryable, auditable, privacy-minimized, and tenant-isolated.

**Non-Goals:**
- Importing journal entries or provider journal lines; allocating split transactions without normalized source lines.
- Writing PaidSoon categories or corrections back to Xero, MYOB, or another accounting provider.
- Using spending category or Jev confidence as a tax/GST decision or as MarginGuard's cost class.
- Running Cost Guard's full alert-detector pipeline; this change provides confirmed category analysis for its existing category surface.
- Automatically confirming any Jev suggestion in the initial release.

## Decisions

### 1. Use a shared analytical assignment, not provider fields or MarginGuard classes

Create tenant-scoped `SpendCategory`, `SpendTag`, `SpendClassification`, `SpendClassificationRule`, and append-only `SpendClassificationEvent` records. `SpendClassification` is unique for a tenant and imported source record and carries the primary category, optional tags, `classificationStatus`, origin, model confidence/probabilities where applicable, source fingerprint, and review metadata. It links to either an imported bill or imported bank transaction; a database constraint requires exactly one source link and tenant-matching composite foreign keys prevent cross-tenant assignments. Rules, categories, tags, assignments, and events have owner-scoped RLS. Events capture actor, timestamp, old/new values, and the applicable rule or model version without storing provider request text.

`SpendCategory` uses a stable tenant-local ID, normalized unique name, description, status, optional `mergedIntoCategoryId`, and a reserved `Other` identity. On first use, provision these defaults idempotently per tenant: `Software & Cloud`, `Professional Services`, `Payroll & Contractors`, `Marketing & Sales`, `Office & Supplies`, `Travel & Transport`, `Facilities & Equipment`, `Banking & Insurance`, `Taxes & Government`, and reserved `Other`; seeded categories remain tenant-editable except `Other`. Normalize names with Unicode NFKC, trim and collapse whitespace, and compare case-insensitively. Retire/merge are soft lifecycle operations, not deletes. Reports can display the original category or roll it up to its merge target. Rename and merge events retain prior names/IDs for historical explanation. Keep the first taxonomy flat and cap the active Jev candidate set at 255 options, including `Other`, because the documented Choice API limit is 255. Reject category creation above that cap until another bounded-candidate strategy is designed. `Other` remains active with its reserved label and cannot be renamed, retired, or merged.

Tags are optional tenant-owned labels with soft retirement and a many-to-many assignment relation. They are not categories, source account data, or accounting dimensions. A normalized merchant/vendor remains a separate classification input; AWS or Azure can be represented as a service/vendor tag while the primary category is `Cloud Hosting`, unless a tenant mapping, rule, or manual correction says otherwise.

**Alternative considered:** Reuse `MarginCostClassification`. Rejected because its mutually exclusive cost classes have different semantics and would make ordinary category reporting ambiguous. Keep MarginGuard's class independent and let it consume confirmed spend category as context.

### 2. Normalize flow direction and account semantics at the provider boundary

Add an explicit normalized bank-transaction direction (`outflow`, `inflow`, `unknown`) to the provider contract and persisted imported transaction. Keep `amountCents` and raw provider data unchanged. Xero `SPEND` maps to `outflow` even when its amount is positive; MYOB banking family determines direction; CSV follows a recognized sign/type mapping and otherwise yields `unknown`. Bills are treated as spend outflows unless the normalized provider status indicates void/draft/non-spend. Category aggregation uses direction and absolute amount, not provider sign conventions.

Only map an expense account when the adapter has actual expense-line/account coding. Keep cash/bank account identifiers separate from expense account metadata in normalized types. The current Xero bill/bank adapters do not provide the same coding granularity as MYOB; absent expense coding means no source-account mapping match, not an inferred category. Reconcile this explicit direction field with existing SpendLeak calculations so Xero outflows are not omitted and inflows are not counted as spend.

### 3. Make deterministic outcomes precede Jev, and make rule propagation explicit

Resolve in this order: (1) manual assignment on the source record, (2) an explicit source-account mapping when provider semantics are verified, (3) a tenant-created enabled rule, ordered by specificity then tenant priority, and (4) Jev for unresolved records. Store both source-account mappings and tenant rules in `SpendClassificationRule`; mappings use `ruleType: source_account`, rules use `merchant` or `text_match`, and the winning row is recorded in `SpendClassification.ruleId` with origin `source_mapping` or `rule`. A source-account mapping is scoped to one `AccountingConnection` and matches verified expense-account code (trimmed, case-insensitive exact match); only when the source has no expense-account code may a normalized expense-account name match. Cash/bank account fields are never mapping inputs. Reject duplicate enabled mapping identities for the same connection and code/name key.

Tenant merchant rules use exact normalized merchant equality. Text rules use a literal normalized phrase contained in the transaction description. Rank an exact merchant match above a text match and longer text phrases above shorter ones; then use higher tenant priority. If top matches have equal specificity and priority but target different categories, mark the record for review. If top matches target the same category, select the smallest stable rule ID for traceability. A correction changes only its transaction by default. The user may explicitly create a rule from that correction and must select its match criteria; rules apply to future records by default, and any historical bulk application requires a separate preview and confirmation. Do not silently convert corrections into merchant rules or transmit prior corrected records as model examples.

Automatic mapping/rule matches can be stored as confirmed with an exact `origin` and rule/mapping reference. If a category or rule is changed, it does not rewrite existing assignments in the background. Historical reevaluation is a distinct explicit action, with manual assignments protected.

### 4. Call the official TypeSafe JavaScript SDK only for unresolved opted-in records

Use the official `@typesafe-ai/sdk` package (`TypeSafeClient.systemOne`) on the server, with `TYPESAFE_API_KEY` only in server environment. The project runs Node 24; the current TypeSafe SDK docs require Node 20 or newer. Pin the initial model to the evaluated version `jev-1.13.0` rather than moving `jev-latest`; record the response's model version and usage. Upgrade the pinned model only after rerunning the evaluation. The SDK's request is a System One state plus Choice question(s); option keys are stable category IDs and option descriptions contain the tenant's category label/description. Validate the response key against the exact submitted active candidate set.

Send a structured state with only: sanitized/truncated transaction description, normalized merchant where known, normalized direction, currency, and a coarse amount band only if the evaluation shows it helps. Include source-account text only when it is verified expense coding. Do not send external source IDs, contact names/emails, references, exact amounts by default, or raw provider payloads. Do not send historical examples. Category labels/descriptions are tenant data too, so classification stays off until the tenant explicitly opts in and receives the external-processing disclosure. Treat TypeSafe's published no-training commitment as distinct from retention: its policy describes retention as necessary and US hosting, with zero data retention described as an enterprise offering.

Use the Choice answer's `choice`, `probabilities`, `confidence`, and `model`; do not expect a rationale field. Show a factual source mapping/rule when deterministic logic won. For Jev, show "Jev suggestion" and confidence/probabilities, not a generated explanation. Every Jev result remains unconfirmed in v1. Use an initial review floor of confidence `< 0.60` or top-probability margin `< 0.15`; always route `Other`, tied results, and invalid/missing responses to `Needs review`. These are operational review flags, not correctness probabilities; report the confidence definition and re-evaluate thresholds against the holdout set.

**Alternative considered:** Call a text-generating LLM and parse a free-form category/rationale. Rejected because Jev's documented Choice response is typed and directly validates against a bounded list; free-form explanation would not be verifiable evidence. **Alternative considered:** Call Jev inside the synchronous accounting-provider sync. Rejected because latency, outages, and rate limits must not make provider ingestion fail or hold its sync lock.

### 5. Persist retryable work and process it in a separately scheduled worker

After source upsert, create or refresh the assignment using tenant/source identity and a fingerprint of classification-relevant normalized fields, direction, active taxonomy version, applicable rule version, and pinned model. Preserve a confirmed manual assignment across re-import. If deterministic logic applies, persist its result locally. If the result is unresolved and tenant opt-in is active, mark it queued; if opt-in is off, leave it unclassified/`Needs review` without sending data.

Add a guarded cron worker with a durable claim/lease so overlapping invocations cannot classify the same assignment. Each invocation claims at most 25 records, with concurrency capped at three and a single active worker lease. External requests happen outside DB transactions. On completion, write the suggestion only if the current source fingerprint still matches and the assignment has not become manual. On failure, persist only a safe error class, attempt count, and retry time. Retry only network, timeout, 429, and 529 failures, for at most three total attempts, with durable delays of 2 seconds and 8 seconds; a provider `Retry-After` value overrides the backoff when it is longer. Route authentication, validation, and other permanent errors to review immediately, and route transient failures to review after the third failed attempt. Keep one request per transaction because Choice returns one category per state; do not batch unrelated records into a single category decision. Provider sync results remain successful when classification is queued or fails.

The worker uses `prismaAdmin` only as documented system processing: it takes user/source/category scope from the database, verifies tenant equality in every claim and write, and never accepts a client-provided tenant ID. User-facing category, rule, review, and correction routes authenticate with Supabase and use `withUserContext`. Add rate limiting and a global worker lease so multiple cron triggers do not exceed provider limits. Add the worker schedule to Vercel configuration and require `CRON_SECRET`.

### 6. Keep review and reporting dimensions explicit

The review surface shows source merchant/description, imported source link, direction, amount/currency, category, status, confidence, and a trustworthy explanation: matched mapping/rule ID and criteria, or a Jev suggestion. It supports single correction, explicit "create rule for future matches," filtered selection, and bulk confirmation of one category for selected records. Bulk confirmation creates an audit event per assignment and never implicitly creates a rule. A rule created from a correction applies only to source records first imported after the rule's creation time; existing records remain unaffected by that rule on all later re-imports. Implement this by comparing the imported record's stable `createdAt` with the rule's `createdAt`, and include only rules created no later than the source record in deterministic resolution and its fingerprint. Manual corrections are never overwritten by later rules or Jev results.

SpendLeak and Cost Guard aggregate only confirmed categories, expose unresolved/unclassified amounts separately, and keep transactions traceable to their imported source. Cost Guard's category endpoint is broadened to bills and bank transactions using normalized outflow direction. MarginGuard may use the category as an input but retains its own cost classification. Tax Buffer continues to depend on source tax metadata and its existing confidence rules; a category or Jev confidence cannot establish GST treatment.

For SpendLeak category reporting, keep bills and bank transactions in separate subtotals and group each subtotal by currency; do not convert currencies or add bills and bank transactions into a combined total that could double-count the same economic spend. Include all imported bills and bank transactions regardless of SpendLeak finding-source selection settings. Preserve assignments on their original category after a merge rather than rolling historical totals up to the merge target. Report eligible outflows with no assignment as unclassified and non-confirmed assignments as unconfirmed; report unknown-direction bank transactions separately, omit inflows from spend totals, and place explicitly excluded plus voided/draft bills in a separate excluded bucket.

Transfers identified by trusted source evidence or an explicit user correction are marked as non-spend and omitted from category totals; the user action stores an audited `excluded` classification with no category and must survive re-import. Do not infer transfer status from description text alone. Refund links are explicit user decisions persisted on the refund classification, constrained to the same tenant and currency and to a confirmed, categorized outflow; cumulative linked credits cannot exceed the original outflow. Same-source-type refund credits reduce the original category/source subtotal. A bank refund linked to a bill is instead reported as a separate bank-transaction credit with traceability to the bill, without netting the bill subtotal. Positive amounts and descriptions alone do not establish refund identity or a link; unlinked refunds and unknown directions remain reviewable. Payroll and tax-payment categories may exist, but neither is tax/accounting advice: Jev remains unconfirmed and ambiguous payment descriptions do not establish tax treatment. Split transactions with provider line rows but no normalized line amounts/categories remain unallocated and in review; do not fabricate allocations.

### 7. Evaluate Jev against a rules-only baseline before any later auto-apply proposal

Create a 300-500 record de-identified or synthetic evaluation set, stratified across Xero, MYOB, CSV, categories, common/rare merchants, recurring charges, ambiguity, credits/refunds, transfers, payroll, and tax-like descriptions. Human-review labels; split by merchant or time so repeated vendors do not leak between tuning and holdout. Compare deterministic rules-only with rules-plus-Jev. Report accuracy and macro-F1, precision among high-confidence suggestions, review rate/coverage, abstention, calibration, p50/p95 latency, tokens and estimated cost per classified record, and failure/retry rates. Do not include raw customer transaction data in the evaluation fixture. V1 still requires user confirmation for every Jev suggestion regardless of benchmark results.

### 8. Additive migration and rollback

Add category, tag, assignment, rule, and audit tables/policies and the normalized direction field with an additive migration. Add an optional same-tenant self-reference on `SpendClassification` for explicit refund links; do not rewrite imported provider source fields. Existing imported spend rows remain untouched and initially unclassified. Provision default categories idempotently on first use; do not backfill historic records through Jev without tenant opt-in. Deploy the data model and user-facing feature disabled, then enable the guarded worker after secrets and schedule are configured. Rollback disables the feature and worker and leaves imported data, refund links, and classification history intact; do not drop user corrections or source records.

## Risks / Trade-offs

- **Provider account semantics differ** → Normalize only fields verified as expense coding; preserve unknowns and route unresolved records through rules/review.
- **Jev confidence is not an individual correctness guarantee** → Keep all suggestions unconfirmed in v1 and use holdout precision/review-rate results before any future auto-apply change.
- **Transaction descriptions and category labels are sensitive** → Explicit tenant opt-in, minimized payloads, no raw provider payloads, no transaction content in logs, and documented TypeSafe processing/retention terms.
- **Worker failures or duplicate cron invocations** → Durable claims, source/taxonomy fingerprints, bounded retries, single-run lease, and idempotent assignment writes.
- **Category merge or rename changes historical display** → Stable IDs, soft lifecycle state, append-only name/merge events, and both original and roll-up report views.
- **Current amount signs are inconsistent** → Add direction without mutating amount fields, then update consumers to filter and aggregate by normalized direction.
- **New taxonomy tables create tenant-isolation risk** → RLS on each tenant-owned table, composite tenant/source/category constraints, `withUserContext` for user operations, and cross-tenant RLS tests.

## Migration Plan

1. Apply the additive schema/policy migration and backfill no provider content; verify RLS isolation for two tenants.
2. Deploy deterministic classification and category settings with external classification disabled by default. Provision default categories on first use.
3. Deploy the retryable worker, configure `TYPESAFE_API_KEY`, `CRON_SECRET`, privacy disclosure, and Vercel schedule; test against mocks and the de-identified evaluation set before enabling an opted-in test tenant.
4. Enable SpendLeak and Cost Guard category summaries only for confirmed assignments; expose unresolved totals separately. Monitor worker success, retry count, token cost, latency, and review rates.
5. To roll back, disable opt-in/worker schedule and category UI, leaving additive assignments, events, and source records intact for later resume or reviewed cleanup.
